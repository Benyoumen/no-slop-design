# No-slop design

**Visual AI slop is manageable.** AI builds a screen in minutes, and the default result looks like every other AI screen: the same gradient, the same three-icon grid, the same rounded cards, the same sentence that says nothing. In 2026 that costs credibility the moment a customer, a sponsor or a candidate opens the page. They cannot say why, but they stop trusting what they see.

The fix is not a designer on every ticket. It is a small set of rules, real data in the mockup, a few checks you can measure, and a habit: validate the screen with the people who will use it before a line of production code exists. This repository holds the rules, the workflow and live mockups built with them.

**See it live:** [the mockup gallery](https://benyoumen.github.io/no-slop-design/): three screens of a broker's assistant for a fictional real-estate brokerage, in the layout of an operator product a broker opens all day, each next to the same screen done the generic way.

## Why a product manager builds and designs now

Product building and product design stopped being optional for a product manager. The tools made the first draft cheap, so the draft is expected, and the person who owns the problem is the right person to make it. What did not become cheap is taste: knowing what the screen should say, what it should not show, and what reads as credible to someone who is not technical.

A readable HTML mockup, validated with stakeholders, is still the fastest way to decide. Faster than a document, because people react to what they see. Safer than a build, because nothing is wasted when they say no. It works for a custom solution inside one company and it works for an agentic system, where the screen has to show what the agent did, what it proposes, and where a person approves.

## Three rules that remove most of the slop

1. **Real data, frozen.** The mockup shows a real snapshot of the system it will replace, anonymized. Invented data approves a screen that does not exist. Where the source has no value, the screen says "no data", never zero.
2. **One generator, never a hand edit.** The HTML is the output of a program. Change the generator, not the file. A mockup edited by hand has three versions of the same button by the tenth round of feedback.
3. **Measure, do not squint.** Contrast, spacing, alignment and clipping are measured in the DOM at two widths. Every defect that escapes becomes a check that fails without the fix.

The full list of visual tells and what to do instead: [`docs/visual-slop-tells.md`](docs/visual-slop-tells.md). The workflow from brief to validated decision: [`docs/mockup-first.md`](docs/mockup-first.md).

## Skills

| Skill | What it does |
|---|---|
| [`html-mockup`](skills/html-mockup/SKILL.md) | Build a high-fidelity HTML mockup from a frozen data snapshot, generated by a script, with tokens first and no hand edits |
| [`visual-slop-audit`](skills/visual-slop-audit/SKILL.md) | Audit a screen against the visual tells: measured checks, two widths, states, copy, and a verdict |
| [`visual-validation-session`](skills/visual-validation-session/SKILL.md) | Run a thirty-minute validation with stakeholders: what to show, the five questions, what to record, how a decision becomes a spec line |
| [`design-tokens-starter`](skills/design-tokens-starter/SKILL.md) | A starter set of tokens and base styles that keeps a mockup consistent without a design system |

Every skill is a folder with a `SKILL.md`: when to use it, inputs, procedure, rules, checklist, an example with a weak and a corrected version, definition of done. They work with Claude Code and similar agents, and as plain Markdown.

## Tools I use next to these rules

- **impeccable**, an open-source set of design skills for coding agents, for craft passes on a surface once the content is right.
- **Web Interface Guidelines** (Vercel), a reviewable list of interface rules for accessibility, forms, motion and typography.
- A **headless browser** to probe behavior and measure the DOM, so the check is a number and not an opinion.

The rules here are about the decisions these tools cannot make for you: what the screen is for, what data it shows, what it must never show, and whether the person who will use it says yes.

## Folders

```
skills/       4 skills, one folder each (SKILL.md)
templates/    tokens file, mockup brief, audit sheet, validation session notes
examples/     acme-realty: the brief, the data snapshot, the audit and the session notes behind the live screens;
              acme-sales-assistant: the same four documents for a field-sales assistant
site/         the mockup gallery, published with GitHub Pages, generated by tools/build_gallery.py
docs/         visual slop tells, the mockup-first workflow, sources
```

The live screens use a fictional brokerage, Acme Realty, and its broker assistant; the earlier example set uses the Acme Field Sales Assistant, an AI agent that drafts follow-up emails after customer meetings. Every name, listing, number and screen is made up for illustration. Nothing comes from a client or an employer.
