# HTML mockup

> A mockup dies two ways: edited by hand, it rots; built on invented data, it lies. This skill prevents both.

## When to use

- A screen or flow has to be validated with the people who will use it, before a line of production code.
- The mockup will go through several rounds of feedback and must stay one version, not three.
- Someone asks to "refresh the data" or "add the real numbers" to a mockup.
- A visual defect escaped and you need a check that catches it next time.
- The screen belongs to an agentic system and has to show presence, proposals, approval and a trail.

Not for a throwaway sketch that will be shown once and deleted. For that, a drawing is enough.

## Inputs

1. The brief ([`templates/mockup-brief.md`](../../templates/mockup-brief.md)): the job, the person, the number, what the screen must never do, the autonomy tier if an agent acts.
2. A snapshot of real data from the system the screen reads, anonymized with a rule you keep private, frozen in JSON with its date.
3. The design tokens ([`design-tokens-starter`](../design-tokens-starter/SKILL.md)) or the real design system's tokens.
4. The rules for the screen type: [dense-operations-ui](https://github.com/Benyoumen/agent-design-principles/tree/main/skills/dense-operations-ui) for operator screens, [agentic-ux](https://github.com/Benyoumen/agent-design-principles/tree/main/skills/agentic-ux) when an agent acts.

## Procedure

1. **Freeze the data.** Export a sample, anonymize names and amounts, record the snapshot date in the file. Keep what the source does not have as `null`; the screen will say "no data", never zero.
2. **Write the tokens first**, in one file: colors, type scale, spacing, radii, one shadow, light and dark. No literal color or size anywhere else.
3. **Write the generator.** One script, standard library only: load data, compute derived values (days overdue, totals, states) from the snapshot date, render each view with small functions, assemble the shell (header, navigation, footer). Output: plain HTML, CSS and a little JavaScript that opens from a file.
4. **Build the four states in version 1**: empty, loading, error, success. Add a small state switcher so a reviewer can reach each state without changing data.
5. **Render the main action from start to result**: the button, what happens, the result message, and the way back (undo or cancel).
6. **Measure.** Contrast on every text pair, clipping, alignment, click targets, keyboard path, at two widths (for example 1280 and 390). Fix, regenerate, measure again.
7. **Run the audit** ([`visual-slop-audit`](../visual-slop-audit/SKILL.md)) and the five-second test with someone who has not seen the brief.
8. **When a defect escapes**, write the check first, run it without the fix to prove it fails, then fix the generator.
9. **Keep the documentation in the gate.** If the tokens or a rule changed and the design notes did not, the mockup is not done.

## Rules

- The generated HTML is never edited by hand. A hand edit is a defect in the generator.
- The data is a frozen snapshot of the real system, anonymized. Nothing invented. Absence shows as "no data".
- The reference date is the snapshot date. Everything relative is computed from it, so the mockup does not age between rounds.
- Tokens live in one place. A color or a size outside the tokens is debt and goes back to the scale.
- Version 1 shows the empty, loading, error and success states. A happy-path mockup approves a product that will live off the happy path.
- Checks test the contract, not the data: "the count in the header equals the rows in the list", never "the count is 12".
- Every check that was written to catch an escaped defect must fail without the fix. A check that never fails protects nothing.
- Audit at two widths. The defect that exists at one width is invisible at the other.

## Checklist

- [ ] Brief with the job, the person, the number and the never list.
- [ ] Data snapshot anonymized, dated, with nulls where the source has nothing.
- [ ] Tokens in one file; no literal color or size outside it.
- [ ] One generator; the HTML opens from a file; nobody has edited the output.
- [ ] Empty, loading, error and success states reachable from the screen.
- [ ] Main action from start to result, with the way back.
- [ ] Contrast, clipping, alignment, targets and keyboard measured at two widths.
- [ ] Audit done, five-second test passed by someone new to the brief.
- [ ] Each escaped defect has a check that fails without the fix.

## Example

Acme Field Sales Assistant, the rep's daily list.

Weak: a page designed in a visual tool with "Customer A, Customer B, $10,000, $20,000", a single happy state, and an approve button that does nothing. The sponsor approves it. Two months later the real list has 60 rows, half of the amounts are missing, and nobody has decided what the screen shows when the agent has nothing to propose.

Corrected: twelve real meetings from the CRM, anonymized, frozen on 2026-04-13, three of them with no amount in the source. The list shows "no data" for those, the header count equals the rows, the agent's proposals sit in their own column with a dashed border and the words "Agent proposes", the approve button writes a result line with Undo, and a switcher shows the list empty, loading and after a failed sync. The session took thirty minutes and produced three decisions and one data gap: the deal stage names in the CRM do not match the ones the reps use.

## Definition of done

The mockup opens from a file, shows real anonymized data with its date, reaches all four states, passes the measured checks at two widths and the audit, and has been through a validation session whose decisions are written as spec lines.
